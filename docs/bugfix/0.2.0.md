# Bug Fixes in v0.2.0

## 1. DROP FUNCTION fails when arg_types contains DEFAULT clauses

**Symptom:**
```
ERROR: syntax error at or near "DEFAULT" (SQLSTATE 42601)
```

**Cause:**
`pg_get_function_arguments()` includes `DEFAULT` expressions in its output
(e.g. `a integer DEFAULT 5`). The restore code passed this string directly
to `DROP FUNCTION`, which does not accept `DEFAULT` in the argument list.

**Fix:**
`internal/ddl/function/generator.go` — added `stripDefaults()` to remove
`DEFAULT ...` clauses from `arg_types` before generating `DROP FUNCTION` DDL.
Top-level comma splitting is used to correctly handle types such as
`numeric(10, 2)` that contain commas inside parentheses.

---

## 2. CREATE TYPE fails for composite types with special characters in field names

**Symptom:**
```
ERROR: syntax error at or near "-" (SQLSTATE 42601)
```

**Cause:**
Composite type field names containing hyphens (`PF-BL`), hash signs
(`#01`), or Japanese characters were written without double-quoting in
the generated `CREATE TYPE` DDL. PostgreSQL parsed `PF-BL` as a
subtraction expression.

**Fix:**
`internal/ddl/compositetype/generator.go` — all field names are now
wrapped in double quotes. Any `"` characters in field names are escaped
as `""`.

---

## 3. Views restored before functions they depend on

**Symptom:**
```
ERROR: function schema.func_name(character varying) does not exist (SQLSTATE 42883)
```

**Cause:**
The DAG dependency resolver did not add edges from views to the functions
they call. As a result, views appeared before functions in the manifest
`restore_order`, and the restore failed when trying to create a view whose
function did not exist yet.

**Fix:**
`internal/restore/orchestrator.go` — Wave 7 is now split into three
ordered passes:
1. functions
2. views and materialized views
3. triggers and policies

This ensures functions are always created before views, regardless of
manifest ordering.

---

## 4. PARTITION BY clause is duplicated in CREATE TABLE DDL

**Symptom:**
```
ERROR: function range(date) does not exist (SQLSTATE 42883)
```

**Cause:**
`pg_get_partkeydef()` returns the full partition key definition including
the strategy keyword (e.g. `RANGE (col)`). The DDL generator additionally
wrapped this with `PARTITION BY STRATEGY (...)`, producing
`PARTITION BY RANGE (RANGE (col))`. PostgreSQL interpreted the inner
`RANGE(col)` as a function call.

**Fix:**
`internal/ddl/table/generator.go` — the `PARTITION BY` clause now uses
`KeyExpression` directly without adding an extra strategy prefix or
parentheses.

---

## 5. Partition child tables cannot be found during restore

**Symptom:**
```
open .../tables/t_child/def.yaml: no such file or directory
open .../tables/t_child/data.csv: no such file or directory
```

**Cause:**
The backup manifest's `restore_order` entries for partition child tables
were missing the `from_table` field. Without it, the restore loader
constructed the path as `tables/<child>/def.yaml` instead of
`tables/<parent>/partitions/<child>/def.yaml`.

**Fix (backup side):**
`internal/resolve/manifest.go` — `ManifestParams` now accepts a
`ChildOf map[string]string` (child name → parent name). The manifest
builder sets `from_table` for each partition child entry in
`restore_order`.

`internal/backup/orchestrator.go` — the `childOf` map (already built for
directory routing) is now passed to `BuildManifest` via `ManifestParams`.

**Fix (restore side — backward compatibility):**
`internal/restore/loader.go` — when `from_table` is absent (backups
generated before v0.2.0) and the direct path does not exist, the loader
scans `tables/*/partitions/<name>/` to locate the correct parent
directory.

`internal/restore/orchestrator.go` — the same fallback is applied in
`copyFromTable` when determining the directory for `data.csv`.
