// Node ID format: "schema.kind.name" e.g. "public.table.users"
// ObjectKind constants: KindTable, KindView, KindMaterializedView, KindFunction,
//   KindSequence, KindTrigger, KindType, KindDomain, KindEnum, KindPolicy, KindForeignKey

type ObjectHeader struct {
    Kind   ObjectKind
    Schema string
    Name   string
}

type ObjectDef interface {
    Header() ObjectHeader

// FunctionDef.ArgTypes, FunctionDef.ReturnType — parse for custom type refs
// DomainDef.BaseType — match against known type names
// TypeDef.Fields[].Type — match against known type names
// ForeignKeyDef — EXCLUDED from DAG, collected separately

Create `internal/resolve/dag.go` with:

1. `NodeID(h core.ObjectHeader) string` — returns `"schema.kind.name"` format.

2. `DAG` struct with:
   - `nodes map[string]core.ObjectHeader` — nodeID to header
   - `edges map[string][]string` — nodeID to list of dependency nodeIDs (things this node depends ON)
   - `inDegree map[string]int` — nodeID to incoming edge count
   - `customTypes map[string]string` — type/domain/enum name to nodeID (for column type matching)

3. `NewDAG() *DAG` — initializes all maps.

4. `AddNode(h core.ObjectHeader)` — adds a node if not already present. Sets inDegree to 0 if new.

5. `AddEdge(from, to string)` — from depends on to. Adds `to` to `edges[from]`, increments `inDegree[from]`. Both nodes must exist (call AddNode first).

6. `AddObject(obj core.ObjectDef) bool` — the main entry point. Returns false for ForeignKeyDef (skipped). For all others:
   - Calls AddNode for the object
   - If Kind is type/domain/enum, registers in customTypes map (key = "schema.name" and also just "name" for unqualified matches)
   - Extracts dependencies by Kind (see dependency rules below)
   - For each dependency found, calls AddEdge if the target node exists in the DAG

**Two-pass design:** Caller should first pass all objects through AddObject to register all nodes (first pass adds nodes + customTypes), then call a separate `ResolveDependencies(objects []core.ObjectDef)` method that does the edge extraction. This avoids ordering issues where a dependency target hasn't been added yet.

Alternative simpler approach: Single pass with deferred edge resolution. AddObject registers the node. After all objects added, call `Resolve()` which iterates nodes and builds edges based on the full node set + customTypes map.

**Dependency extraction rules:**
- `table`: Parse each column's Default with regex `nextval\('([^']+)'` to find sequence deps. Check each column's Type against customTypes map.
- `trigger`: Add edges to `schema.table.TableName` and `schema.function.FunctionName` (same schema as trigger).
- `policy`: Add edge to `schema.table.TableName` (same schema as policy).
- `function`: Check ArgTypes and ReturnType against customTypes map (split on comma, trim spaces).
- `domain`: Check BaseType against customTypes map.
- `type` (composite): Check each Fields[].Type against customTypes map.
- `view`, `materialized_view`: Use type-priority ordering. These depend on all tables in the same schema (conservative approach per research recommendation). Actually, simpler: assign a priority tier and during Kahn's sort, use tier as tiebreaker. OR: don't add explicit view->table edges; rely on type-priority tiebreaking in Kahn's sort (see Task 2). **Chosen approach:** Add no automatic edges for views/matviews. Instead, in kahn.go, the sorted zero-in-degree candidates use a priority order: sequence < enum < type < domain < table < view < materialized_view < function < trigger < policy. This ensures correct ordering without fragile dependency guessing.
- `sequence`, `enum`: Leaf nodes, no edges.
- `foreign_key`: Skip entirely (return false).

**nextval regex:** `nextval\('([^']+)'` — extract group 1. Strip `::regclass` suffix if present. Normalize: if contains `.`, split into schema.name; otherwise assume same schema as the table. Build target nodeID as `schema.sequence.seqname`.

Create `internal/resolve/kahn.go` with:

1. `kindPriority` map — assigns numeric priority to each ObjectKind for deterministic tiebreaking when multiple nodes have in-degree 0:
   ```
   sequence: 0, enum: 1, type: 2, domain: 3, table: 4, view: 5,
   materialized_view: 6, function: 7, trigger: 8, policy: 9
   ```
   This ensures the natural restore order even without explicit edges.

2. `(d *DAG) TopologicalSort() ([]core.ObjectHeader, error)` method:
   - Copy inDegree map to avoid mutating DAG state
   - Collect initial zero-in-degree nodes
   - Sort candidates by (kindPriority, schema, name) for determinism — use a `sort.Slice` with the priority map
   - Standard Kahn's loop: pop first candidate, append to result, decrement in-degree of nodes that depend on popped node (reverse adjacency scan), add newly zero nodes to candidate list, re-sort
   - After loop: check `len(result) == len(d.nodes)`. If not, collect remaining nodes with in-degree > 0 and return error: `"circular dependency detected among: [node1, node2, ...]"`
   - Return `[]core.ObjectHeader` (resolve nodeID back to header via `d.nodes` map)

3. `BuildRestoreOrder(objects []core.ObjectDef) ([]core.ObjectHeader, error)` function:
   - Separate ForeignKeyDef objects from others
   - Create DAG via NewDAG()
   - First pass: AddObject for all non-FK objects (registers nodes + customTypes)
   - Call dag.Resolve(objects) to build edges (the deferred edge resolution from Task 1)
   - Call dag.TopologicalSort() — if error (cycle), return it
   - Append FK headers to the end of the sorted result (sorted by schema.name for determinism)
   - Return combined order
